Architecture Brief

What RAIL Is, What Feels Solid, and What Still Feels In Progress

A digestible snapshot of RAIL after the repo-first migration work, framed against the “follow goals” pattern used in Codex-style systems.

Prepared: May 29, 2026 Audience: product, engineering, research ops

Bottom line

RAIL is a repo-native research agent platform. It is not “done” as a product, but the core repo-first architecture milestone is now substantially implemented and working.

What RAIL is architecturally

RAIL is best understood as a control plane for research projects where the project repo is supposed to become the durable system of record. The repo holds project configuration, task state, session artifacts, lineage, verification records, and hydration metadata. The platform then layers APIs, dashboards, agents, and automation on top of that repo truth.

In that sense, RAIL combines four roles that are often separate in other systems:

Research operating system

It manages tasks, sessions, artifacts, questions, approvals, and closeout work for a project rather than just storing files.

Agent execution layer

It launches and tracks worker sessions, planner loops, hydration runs, and recovery paths for background execution.

Integrity and provenance layer

It records sources, claims, verification runs, lineage, and evidence so that outputs can be trusted rather than merely generated.

Repo-backed UI platform

It serves planner, dashboard, review, agent, ontology, and evidence views from reconciled project state instead of treating the UI as a separate truth system.

The linked OpenAI “follow goals” idea maps well here: define an objective, keep running until complete or blocked, and use evidence to decide whether the work is actually done. RAIL extends that pattern from a single goal-following agent into a full project platform.

What parts are solid now

The strongest improvement is that repo-backed state is no longer just an aspiration. It is now the primary read path for many important product surfaces.

  • Major UI surfaces now read repo-backed or snapshot-backed state, including planner, overview, dashboard, zen, runs, review, ontology, sources, artifacts, integrity, settings, and agent pages.
  • `planner/home` and `control_plane_snapshot.json` have become real shared summary contracts rather than side experiments.
  • Repo-only projects work much better across activation, reconciliation, hydration, dashboarding, job routing, context uploads, GitHub linkage, and SQL or ontology reads.
  • A large number of Convex-first reads were replaced with shared repo-first resolution, which means the platform degrades more gracefully when backend state is absent or stale.
  • Broad focused regressions and live route checks passed during the migration, which gives this milestone real verification rather than just architectural intent.

The most important architectural result is not “there is less Convex.” It is that more of the platform now agrees on where truth lives, and that makes behavior easier to reason about.

What still feels unfinished

RAIL is in a much healthier state, but it still feels like an evolving platform rather than a finished product. The remaining gaps are narrower than before, but they are real.

  • Some direct backend mutation and canonical lookup paths still intentionally go through Convex, so this is repo-first, not repo-only.
  • There is still architectural cleanup available around which surfaces should remain live overlays versus which should always be served from reconciled snapshots.
  • Documentation and operator guidance still lag the implementation, which makes the system harder to explain than it now deserves.
  • Product maturity is uneven: core control-plane behavior is much stronger than the surrounding polish, onboarding, and long-term maintainability story.
  • “Done” for RAIL as a whole would mean a stable product contract, not just successful architectural migration. That is not the same milestone.

Practical answer

If the question is “Is RAIL real?”, the answer is yes. If the question is “Is the repo-first architecture milestone done?”, the answer is also basically yes. If the question is “Is RAIL fully finished as a platform?”, the answer is no.

The honest framing is that RAIL now has a much more coherent architectural center. What remains is product hardening, cleanup, and continued narrowing of the places where old and new truth models still coexist.

Prepared from the current codebase state and migration work completed in late May 2026.
